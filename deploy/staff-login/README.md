# Private CRM login Compose candidate

This is an **alternate Compose Path** for the existing staff-inspection project; it does not change the original manifest. It has no routes, published ports or automatic starts through Git. Leave the original project saved configuration alone until a reviewed change is approved. The inspection service is **not in this manifest** and must never be attached to either public hostname. Do not use the general Supabase gateway for this login path.

## Service discovery and target

`docker compose -f docker-compose.staff-login.dokploy.yml config --services` lists `crm` and **`login-gateway`**, with no profiles (the same output with `--profile '*'`). The eventual Dokploy source path is `./docker-compose.staff-login.dokploy.yml`. The exact target for **both** HTTPS hostnames is **`login-gateway`, internal port `443`, HTTPS upstream**. Preserve Host and TLS SNI verification, with a certificate valid for the exact two origins. Do not select `crm`, `inspection`, `auth`, or `rest` as a route target. No Dokploy or edge action is authorized by this document. Compose CLI discovery does not establish any hosted Dokploy UI behavior.

For an approved private rehearsal only, with verified inputs and fenced topology:

```sh
docker compose --project-directory . -p REVIEWED_PROJECT --env-file REVIEWED_LOGIN_ENV -f docker-compose.staff-login.dokploy.yml up -d --no-build --pull never crm login-gateway
```

- `LOGIN_CRM_IMAGE` and `LOGIN_GATEWAY_IMAGE` select preloaded exact image IDs/digests (Compose cannot enforce immutable selectors). Build the gateway from this directory with a verified `LOGIN_RUNTIME_IMAGE` base. It bundles no dependencies or keys. A Linux/ARM64 archive was built and verified locally; review and preload it before any staging start.
- `LOGIN_GATEWAY_MODE` is **disabled** by default (the gateway exits 78 without opening a listener). `private-fixture-v1` restricts the listener to reserved fixture origins and the synthetic anon marker. `private-staging-v1` accepts only the exact staging pair, `wacrm-staging.sqkii.land` and `wacrm-api-staging.sqkii.land`, and the public Auth anon token. These are test modes, not an edge approval control.
- `LOGIN_INPUT_DIR` points to a dedicated **private** directory, not a repository or a shared config tree. Supply read-only `anon` (matching the CRM build-time public anon key), `ca.pem` (a pinned private fixture leaf for the dry run), `gateway/key.pem` (readable only by owner UID 1000), and `gateway/upstreams.json` (`owner`: synthetic GoTrue UUID; `auth` and `rest`: verified staging-private IPv4 addresses). Fixture Auth/REST ports are 19999/3101; staging ports are 9999/3000. The CRM gets only the anon file and public certificate. The gateway verifies the bearer against GoTrue `/user` and pins the exact owner plus authenticated claims. It has no JWT signing key, DB password, service-role key, or inspection credential. `docker compose config --quiet` validates without emitting config; read-only mounted inputs are not interpolated into Compose.
- `login-front` is internal, and only `login-gateway` joins `LOGIN_UPSTREAM_NETWORK`. CRM uses the exact API DNS alias for SSR. **Before starting on a non-internal upstream network**, provide and enforce the reviewed gateway-namespace egress fence to exact upstream destinations; this manifest does not install that fence. Disable/no listener is not a network isolation proof. No DB, Studio, signup/admin, broad REST, WhatsApp, inspection or mutation routes; use only the allowed login/dashboard/inbox-read paths.

## Evidence and hold

`node --test deploy/staff-login/compose-contract.test.mjs` passed with Docker Compose v5.7.0: default and all profiles discover exactly two services, only gateway port 443 is declared internally, no host ports, no extra networks or service-key/credential markers in config. Two fresh local synthetic runs exercised the effective Compose services with real disposable GoTrue, PostgREST and PG plus the unchanged amd64 CRM. Chromium verified TLS, password login, dashboard RPC, legitimate profile and conversation reads carrying the SDK retry header, SSR reload, seeded inbox message, menu logout, and signed-out dashboard/inbox denial. The observed 403 came from a CORS preflight rejecting `x-retry-count` on a PostgREST SDK retry. The gateway permits the marker only for allowlisted REST GET preflights and does not forward it upstream; method, path, origin, account and authorization checks are unchanged. Forced token expiry was not re-run on this Compose candidate. The synthetic runner is outside Git (`wacrm-staging-artifacts/normal-https-login/rehearse-compose-login.py`).

**Still required for exposure:** review/preload the Linux/ARM64 archive and verify its runtime behavior, exact mounted-file and upstream IP wiring and drift policy, gateway namespace fence, independently reviewed host routing and verified edge-to-origin TLS, no direct-origin bypass, and non-bypassable edge/Auth rate limits. Socket-IP limits in this gateway are a bounded private safeguard, not trusted edge client identity. Roll back by closing **both** precise trial routes first and stopping only the two trial services; keep the original inspection paths and backend unchanged.
