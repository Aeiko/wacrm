# Permanent WACRM email registration candidate

**Not live.** Reuse the installed multi-account Next image: `/login` already links to the signed-out `/signup` form, whose Supabase SSR client submits email/password with an S256 PKCE challenge and a dashboard callback. No application rebuild, SQL migration, invitation, or administrative client is required. The gateway retains independently gated reply and Connect routes. This package does not enable those features or replace the full CRM.

## Boundaries

- The exact public paths are CRM `/signup` and `/auth/callback`, API `/auth/v1/signup` (POST/OPTIONS), and API `/auth/v1/verify` (GET/POST). The PKCE exchange route is private to the existing CRM socket peer; no public Auth grants or recovery/admin routes are added. The gateway flag defaults to off.
- Sign-up bodies are rebuilt from email, password, S256 challenge and full name only. GoTrue must require email confirmation with anonymous and phone signup off. The existing `handle_new_user` trigger creates a fresh workspace and grants ownership of **that workspace only**; the Auth role stays `authenticated`. Before verification there is no usable session. No DB grants or membership rules are changed.
- The confirmation URL lands on a no-store, no-referrer page. Merely opening the email URL does not consume it; a button submits the token. The gateway passes only the fixed signup type and permanent callback to GoTrue. The existing callback exchanges the code using the original browser's verifier cookie; on a different browser, verify, then sign in normally. Do not substitute a custom implicit-flow or click-tracking template.
- Separate signup (3/min), verification POST (20/min), callback and private exchange lanes do not spend the existing password/refresh budgets. GoTrue additionally limits email sends to 12/hour and repeats to the same address to once per 120 seconds. The ceilings are intentionally global on the current single gateway; a sustained bot can exhaust the signup lane without blocking login. No CAPTCHA vendor or paid service is required for this candidate.

## Release gate and rollback

1. The saved permanent Auth input specifies invite-only signup and has fixture SMTP settings (port 1025, fixture sender, no SMTP authentication). That does not establish working delivery to real inboxes. **Need an approved working SMTP relay/sender and one mailbox we control.** Do not open public signup with Mailpit/autoconfirm. Do not mail third parties during rehearsal. Have the mail operator provision a WACRM-only relay identity and approved sender directly into the restricted deployment secret store or a root-owned `0600` Auth env file on the authorized deployment host. Use the `WACRM_REG_SMTP_*` names in `auth.compose.yml`; do not send credentials, codes, or verification links through chat or Git. Separately reestablish trusted access to the authorized deployment host for cutover.
2. Coordinate with the current gateway owner before changing any running container, image pin, bridge script, or routes. Read back the actual gateway, CRM and Auth pins and exact route files. Apply the registration delta to the newest verified gateway, retaining already-published reply/Connect routes and the existing namespace fence. Do not deploy this standalone baseline over a newer gateway. Preserve the current permanent Auth config (not the pre-permanent/staging rollback), with a private copy of only the touched configs for rollback.
3. Build the gateway with `Dockerfile.gateway` and the pinned node base `docker.io/library/node@sha256:1314fb30ec37592d5845e5a160d522c0e680972aa534549940b8d73bde88481a` for `linux/arm64`. Verify the expected source/image pins. `node --test deploy/public-registration/gateway.test.mjs` runs the isolated HTTP contract. Repeat the disposable GoTrue/Mailpit verification and workspace isolation rehearsal before cutover. Fetch authoritative Cloudflare ranges from `https://api.cloudflare.com/client/v4/ips`, render with `routes.py inert`, verify direct-source denial, method split, rate limits and no fallback, then discard the inert file. Do not edit the existing login router or change standard TLS. Confirm no edge/Traefik/Auth/CRM logging captures raw verification queries, callback codes, passwords or cookies; bypass edge caching on sensitive routes. The route file explicitly disables Traefik access logs and tracing for these paths.
4. Overlay `auth.compose.yml` on the existing **isolated** Auth Compose inputs; supply `WACRM_REG_SMTP_*` privately. Compare the rendered Auth service against the live one without printing env values, and require only the registration settings to differ. Check that GoTrue has no alternate public ingress. Recreate Auth **only**, refence the gateway to the actual Auth IP, and leave public registration closed while running an owned-address acceptance through a temporary private route. Require no password session before confirmation, real delivery, correct permanent link, confirmation, sign-in, and a new isolated workspace. Check synthetic owner cleanup independently; never touch existing users. The current private-origin launcher asserts `GOTRUE_DISABLE_SIGNUP=true`; at cutover replace that single check with an explicit registration-mode branch requiring `GOTRUE_DISABLE_SIGNUP=false`, email enabled, anonymous/phone/autoconfirm disabled, and the exact permanent URLs. Pass `LOGIN_PUBLIC_EMAIL_REGISTRATION=true` only to the fenced gateway in that branch. Publish `routes.py live` as a separate file only once every gate passes.
5. For rollback, remove only the registration route file, then disable the gateway flag and restore the prior permanent Auth-only config; refence if its address changes. Verify the existing login, SSR, reply/Connect, and webhook routes still behave as before. Rollback does not delete confirmed users or change existing memberships.
